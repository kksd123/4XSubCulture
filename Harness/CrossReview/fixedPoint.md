# 교차검증 사례 — 고정소수점 결정성

> **AI 오케스트레이션 워크플로우 실증 자료.** 결정성 토대(고정소수점)를 설계한 모델과
> **다른 벤더 모델로 적대적 교차검증**하고, 그 지적을 그대로 수용하지 않고 **직접 검증·취사선택**한 기록.
> 원시 증거(검증자 응답 원문 전문)는 [`2026-06-30_fixedpoint.md`](./2026-06-30_fixedpoint.md)에 별도 박제.

---

## 한 줄 요약
설계자 모델(**Claude Opus 4.8**)이 만든 고정소수점 결정성 토대(`SimCore/fixed.h`)를, **동일 모델 자기평가 편향을 피하기 위해** 다른 벤더 모델(**GPT-5.5**)로 적대적 리뷰시키고, 16건의 지적을 **데싱크/정확성/설계로 분류해 직접 채택·기각**했다.

---

## 1. 왜 이 검증을 했나
- **고정소수점은 결정성의 단일 토대** — 여기가 틀리면 멀티플레이 데싱크로 직결된다. 가장 검증이 필요한 지점.
- **자기평가 편향 회피** — 설계를 한 모델(Claude)에게 "잘 짰냐"고 물으면 편향이 낀다. 그래서 **다른 벤더(GPT)** 에게 적대적으로 반례를 찾게 했다.
- **목적은 버그 사냥이 아니라 방법론 실증** — "타 모델 교차검증이 실제로 결함을 잡고, 내가 그걸 걸러낼 수 있는가"를 확인하는 실험.

## 2. 셋업
| 항목 | 값 |
|------|-----|
| 검증 대상 | `SimCore/SimCore/fixed.h` (Fixed 타입 + 연산자 `+ - * /` + `ToInt`/`ToFloat`) + 사용 맥락(`sim_core.cpp`, `SimCoreTest.cs`) |
| 설계자 모델 | Claude Opus 4.8 (추론: 높음) |
| 검증자 모델 | GPT-5.5 (추론: 높음) — **다른 벤더** |
| 방법 | 적대적 리뷰 프롬프트: 칭찬 금지·반례 우선, **데싱크 vs 정확성 구분 강제**, "x64라서 괜찮다" 변명 차단(언리얼 이식 전제), 읽기 전용(파일 수정 금지) |
| 채점 기준 | 검증 전 미리 세운 **기대 답안 4건**과 대조 → 놓침/새발견/오답 3분할 |

## 3. 결과 한눈에
- **지적 16건 — 채택 14 · 부분(범위 밖) 1 · 프레이밍 기각 1.**
- 검증자가 **기대 답안 4건을 전부 포착**(곱셈 오버플로 · 음수 floor · float 경계 · 헌법 규칙 부재) + 새 발견 다수.
- **치명적 결함 TOP 3** (실제 코드로 재확인됨):
  1. `operator + - * /` 전반의 signed overflow / 음수 shift / 0분모 **UB** → 컴파일러·플랫폼 무관 비트 동일성을 깨뜨림 (`fixed.h:18~21`)
  2. 곱셈/나눗셈 **중간값이 64비트** → 정상 게임 범위처럼 보이는 값(`100000 * 100000`)도 INT64_MAX 초과 (`fixed.h:20~21`)
  3. C ABI `sim_spawn`이 **외부 raw를 무검증 주입** → 한 틱 뒤 UB 가능 (`sim_core.h:21`, `sim_core.cpp:56`)

## 4. 핵심 — AI 지적을 '그대로' 받지 않았다 (이 사례의 본질)
교차검증의 가치는 "AI가 버그를 찾았다"가 아니라 **"내가 그 지적을 판별했다"**에 있다. 두 장면:

**① 반박한 지적 (C14) — 아키텍처 규칙으로 기각**
검증자는 *"`Time.deltaTime` float 누적으로 틱 횟수를 정하니 데싱크"*라고 지적했다. 그러나 **벽시계로 틱 cadence를 정하고 Sim 상태는 정수 틱으로만 올리는 것은 본 프로젝트가 인가한 '두 시계' 패턴**이다(Harness §3-1). Fixed 산술 결과는 틱을 몇 번 돌리든 비트 동일하므로 **이 지적은 고정소수점 결정성과 무관**하다. 그 밑에 깔린 진짜 빈틈(락스텝 게이트 `CanAdvanceTick` 부재)은 **네트워크 단계의 이미 알려진 미구현**이라 이번 범위 밖. → **"float=데싱크" 프레이밍은 기각**, 실제 항목은 별도 분류.

**② 채택한 새 발견 (C8) — 기대 답안에도 없던 통찰**
검증자는 *"곱셈은 `>>`라 floor 방향, 나눗셈은 C++ 정수나눗셈이라 0방향 절삭 — 두 연산의 라운딩 정책이 섞여 있다"*고 지적했다. 이는 내가 미리 세운 기대 답안에 **없던 새 발견**이며, 위치 누적의 예측 가능성을 해치는 실재 문제라 **수용**했다.

> 즉 무비판 수용도, 무시도 아닌 **판단**. 이 판별 능력이 "AI를 코드 생성기가 아니라 검증 파트너로 통제한다"의 실체다.

## 5. 채택 / 기각 표 (전체 16건)

| # | 지적 | 심각도 | 분류 | 판정 | 사유 |
|---|---|---|---|---|---|
| C1 | `operator+` signed overflow UB | 상 | 데싱크 | 채택 | int64 overflow=UB. 현재 테스트값은 작아 안전하나 타입이 강제 안 함 |
| C2 | `operator-` overflow(INT64_MIN 부호반전) | 상 | 데싱크 | 채택 | 미사용이나 타입 계약은 열림. 거리/방향에서 곧 사용 |
| C3 | `operator*` 64bit 중간값 오버플로 | 상 | 데싱크 | **채택 ★핵심** | `100000*100000`→4.29e19>INT64_MAX. 128bit 중간값 필수 |
| C4 | `operator/` shift 오버플로 + 음수 left shift | 상 | 데싱크 | 채택 | `a.raw<<16` 오버플로 + signed left shift는 C++20 이전 UB |
| C5 | `operator/` 0 분모 무검증 | 상 | 데싱크 | 채택 | 정수 div-by-zero=UB. 타입이 안 막음 |
| C6 | 음수 right shift 이식성 | 중 | 데싱크 | 채택(보류성) | pre-C++20 구현정의. 실무 위험은 낮으나 계약상 명문화 |
| C7 | 곱셈 음수 rounding 편향 | 중 | 정확성 | 채택 | 극소 음수곱이 -1 LSB로 floor. 라운딩 정책 부재 |
| C8 | 곱셈 floor vs 나눗셈 trunc 혼재 | 중 | 정확성 | **채택 ★새발견** | `*`는 floor, `/`는 0방향 절삭. 정책 불일치 |
| C9 | `ToInt` 음수 floor→셀 -1 | 중 | 정확성 | 채택 | 원점 왼쪽 극소오차가 타일 -1로 |
| C10 | `ToInt` int32 narrowing | 중 | 데싱크 | 채택 | `1<<62>>16` int32 범위 밖→구현정의 |
| C11 | `ToFloat` 정밀도 손실 | 중 | 정확성 | 채택(규칙화) | render-only인데 Sim 역류 시 위험 → 규칙으로 봉인 |
| C12 | `sim_spawn` raw 무검증 주입 | 상 | 설계 | **채택 ★새·시스템적** | ABI가 INT64_MAX raw 허용→다음 틱 UB. 경계 검증 필요 |
| C13 | C# `ONE=65536` 스케일 중복 | 중 | 설계 | **채택 ★새** | `SimCoreTest.cs:63` const + `:42` 매직리터럴. C++ `SHIFT`와 이중계약 |
| C14 | `Time.deltaTime`→tick 횟수 | 중 | 데싱크 | **부분채택/범위밖** | accumulator는 인가된 '두 시계' 패턴. "float=데싱크" 프레이밍 기각, 게이트 부재는 별도·범위 밖 |
| C15 | public `raw` 불변식 우회 | 하 | 설계 | 채택(경미) | `fixed.h:6` raw public. 캡슐화 vs POD 편의 트레이드오프 |
| C16 | 고정소수점 헌법 8조항 + TOP3 제안 | — | — | 채택 | Harness §2 "고정소수점 규칙" 신설 입력으로 사용 |

## 6. 기대 답안 대비 3분할 (검증의 검증)
- **놓침**: 사실상 없음(기대 4건 전부 포착). 굳이 꼽으면 *0.1 같은 십진 소수의 항구적 양자화*를 C11이 정밀도 측면으로만 다루고 직접 명명은 약함 — 경미.
- **새로 찾음**: C2·C4·C5·**C8(라운딩 혼재 — 가장 인상적)**·C10·**C12(ABI 무검증 — 시스템적)**·C13·C15.
- **틀린/오해**: C14의 "float accumulator=데싱크" 프레이밍(인가 패턴 + 게이트 부재는 범위 밖). C6은 타당하나 severity 약간 과장.
